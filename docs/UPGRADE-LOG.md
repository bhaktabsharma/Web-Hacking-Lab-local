# vNEXT Upgrade Log

This tracks progress against the "MASTER UPGRADE PROMPT — WEB HACKING LABS
vNEXT" spec (71 sections: realism overhaul, new categories, GraphQL/
WebSocket depth, business logic, attack chains, isolation tests, a
reporting system, and more). That spec is a multi-week engineering project
end to end. This log exists so any session — human or Claude — picking this
back up later knows exactly what's done, what's next, and why decisions
were made the way they were.

**Golden rule, unchanged from the spec:** `cd web-hacking-labs && npm
install && npm run dev` → `http://localhost:3000`. Every phase below must
leave that working.

## Phase 1 — Architecture: core engines, session hygiene, lab metadata ✅ DONE

**Scope actually completed** (see "Scope note" below for what was
deliberately deferred and why):

1. **`src/core/*-engine` extraction (Section 6).** `routes/vuln-common.js`
   (283 lines, everything from sessions to fixtures to page chrome in one
   file) is now a thin backward-compatible facade over:
   - `src/core/session-engine`, `src/core/state-engine`,
     `src/core/flag-engine`, `src/core/progress-engine`,
     `src/core/hint-engine`, `src/core/reset-engine`
   - `src/services/fake-filesystem.js`, `src/services/fake-internal-network.js`,
     `src/services/page-shell.js`
   - `src/labs/fixtures/users.js`
   - `src/utils/random.js`, `src/utils/difficulty.js`

   Every one of the 12 route files still does `const C =
   require("./vuln-common")` — **zero route files were touched.** This was
   a pure extract-and-delegate refactor specifically to avoid touching the
   87 labs' actual route logic. Verified via the full test suite (still
   100% green) plus a manual smoke test against a live server before and
   after.

2. **Session TTL / cleanup / capacity cap (Section 57).** Session records
   now carry `createdAt`/`lastAccess`. A background sweep (every 10 min,
   `.unref()`'d so it can never keep the test runner's child process alive
   on its own) evicts sessions idle more than 2 hours. A soft 5000-session
   cap evicts the least-recently-used session before exceeding it. New
   `tests/session-engine.test.js` (18 assertions) covers creation, reuse,
   an unrecognized-cookie edge case, TTL expiry, and capacity eviction as a
   pure unit test against the module — no live server needed.

3. **Centralized lab metadata — `tags` and `successCondition` (Section
   13).** Added via a one-time, source-text-preserving migration
   (`tools/enrich-lab-metadata.js`) to all 87 labs. `tags` is derived
   mechanically (category + id tokens, not hand-typed) so it can't drift
   from what a lab actually is. `successCondition` records which of the
   platform's two real success mechanisms a lab uses (ordinary
   server-verified flag, or the client-proof-token flow for
   client-side-only exploits like DOM XSS) — grepped from the actual route
   source, not guessed.

**A bug I introduced and caught before it shipped:** the first version of
this migration also tried to add `chainId` and a fresh `prerequisites`
array to every lab. For the 3 attack-chain labs, that silently collided
with a `locked: true, prerequisites: [...]` field that **already existed**
later in those same lab objects (built in an earlier session — I'd missed
it in the Phase 0 audit because I only inspected the first ~60 lines of
the file as a representative sample, not the full 2000+ lines). JS object
literals let a later duplicate key silently win, so the app's actual
runtime behavior was never wrong — but the source would have shipped with
two conflicting `prerequisites:` fields in the same object, exactly the
duplication the spec's Section 5/60 warns against. I caught it by diffing
the migration's output against the original file line-by-line before
running the full suite (the same discipline as every other change in this
log), traced the unexpected values back to the pre-existing field, and
removed my own `chainId`/`prerequisites` addition entirely rather than
trying to reconcile two versions — the existing `locked`/`prerequisites`
mechanism (which `public/js/app.js` already reads, including a documented
"no explicit list = solve everything" fallback for the `final` lab) is
more precise than what I'd invented anyway. `tests/lab-metadata.test.js`
now includes a referential-integrity check (every prerequisite id must
exist in the registry) specifically so a mistake in this family fails the
build immediately next time instead of needing to be caught by hand.

**Scope note — deferred from this phase:** the spec's Section 55
("consistent platform API responses, `{success, data, error}`") is NOT
done yet. The `/api/*` endpoints already return `{success, ...}` shaped
JSON, just not identically shaped across all six of them (e.g.
`/api/progress` returns `{solved, hintsUsed}` with no top-level
`success`). Normalizing this properly means also updating
`public/js/app.js`/`public/js/lab.js` (the frontend consumers) and several
existing tests that assert on today's exact field names — real, doable
work, but coupled work that deserves its own focused pass rather than
being rushed alongside an unrelated engine-extraction refactor. Tracked
for Phase 7 (final polish pass) rather than silently dropped.

## Phase 3a — New lab: CSP Bypass (Section 27) ✅ DONE (first increment)

**Audit before adding anything, per Section 3.** Before writing new labs, I
checked what the spec asks for in Sections 17–31/64–66 against what
already exists, because the codebase turned out to be far more complete
than the spec's checklist implies — this is a mature, previously
multi-session-built platform, not a bare scaffold. Confirmed already
present and solid:

- **LDAP injection, XPath injection** (Section 17) — already exist
  (`ldap-injection`, `xpath-injection`), part of 16 injection labs total.
- **Real, non-magic-parameter race conditions** (Section 31's explicit
  anti-pattern warning) — audited `routes/vulns-serverlogic.js`'s
  `race-conditions` lab directly: it fires genuinely concurrent
  `Promise.all()` HTTP requests against real shared server-side state (a
  gift-card balance) with a real check-then-act timing gap. This is
  exactly the pattern the spec asks for, already correctly implemented.
  **No fix needed** — worth recording so a future pass doesn't re-audit it.
- **Request smuggling, cache poisoning, cache deception, host-header
  issues** (Section 30) — all already exist as dedicated labs.
- **OAuth, JWT, MFA, password reset, session management** (Section 19) —
  all already exist, several as dedicated labs with their own difficulty
  tiers (`oauth-misconfig`, `jwt-vulnerabilities`, `2fa-bypass`,
  `password-reset`, `session-fixation`, `weak-session-token`, etc.)

**Genuine gap found: CSP.** The only pre-existing CSP touchpoint anywhere
in the codebase was the `clickjacking` lab's `frame-ancestors` directive —
about framing, not script-execution bypass. Section 27 explicitly asks for
"CSP training" and "CSP weaknesses" as their own content. Added
**`csp-bypass`** (client-side category) — a genuinely new lab, not a
variant of an existing one:

- **easy** — `script-src 'self' 'unsafe-inline'`: the #1 real-world CSP
  mistake (a policy exists but still allows inline scripts).
- **medium** — `script-src 'self' 'unsafe-eval'`, reached through a
  realistic "internal Formula Preview" tool that naively `eval()`s user
  input.
- **hard** — a nonce-based policy that looks correctly configured, except
  the nonce is a static value that never rotates per-request — a real,
  documented anti-pattern (a nonce that doesn't change provides no real
  protection).

All three tiers set a **real** `Content-Security-Policy` response header
(verifiable with `curl -I`, exactly per Section 38's "must be reproducible
with normal HTTP traffic, not a click-to-exploit button"). Getting this
technically accurate required one real architecture decision: the app's
own legitimate JS had to move to an external same-origin file
(`public/js/csp-bypass-app.js`, loaded via `<script src="...">` rather
than inline) so it keeps working under `'self'` even when
`'unsafe-inline'` is absent — inline `<script>` blocks inserted via
`innerHTML` don't execute in real browsers regardless of CSP, so the
vulnerable "note" reflection is server-rendered directly into the raw HTML
response (matching how the existing `xss` lab already reflects input),
making it something a real browser genuinely parses and executes, subject
to real CSP enforcement.

Uses the same client-proof-token flow as `dom-xss`/`cstl`/`postmessage`/
`prototype-pollution` (the exploit's success can only be observed
client-side — the server has no way to know whether the browser's CSP
allowed a script to run). New `tests/csp-bypass.test.js` (36 assertions)
covers header correctness per tier, the nonce-non-rotation bug directly
(reload and diff), and the full token issue/confirm/replay/reset
lifecycle — mirroring the exact test pattern already established for the
other four client-proof-token labs in `tests/engine.test.js`.

**A bug I introduced and caught in my own str_replace edit:** writing the
new lab's `labs-data.js` entry, my edit accidentally deleted the
`header-xss` lab's opening `{ id: "header-xss", ... }` line — a copy-paste
anchor mistake, not a design issue. `node --check` immediately caught the
syntax error before anything else ran; fixed by re-adding the dropped
line, then re-verified header-xss's full entry was otherwise untouched.

**Result:**

## Phase 6 — Isolation & security test suites ✅ DONE (Sections 47–50)

The spec explicitly requires this to be *proven*, not just asserted — three
new permanent test files, each combining static source analysis with live
dynamic fuzzing against the running server:

**`tests/ssrf-isolation.test.js`** (21 assertions) — confirms no route/src
file ever `require()`s `http`/`https`/`net`/`dns`, so a real outbound
request is not just unlikely but structurally impossible from this code.
Dynamically fuzzes `/vuln/ssrf` with loopback/RFC1918/public-domain
payloads that share no host string with any allowlisted fake service and
confirms none of them produce a response — only the exact allowlisted
keys do.

**`tests/filesystem-isolation.test.js`** (49 assertions) — confirms the
real `fs` module is required in exactly one place in the whole codebase
(the file-upload feature's own multer-managed sandbox directory, never
fed anything from request input), and that path-traversal/LFI resolve
exclusively through the fake VFS object. Dynamically fuzzes both routes
with real host paths (`/etc/passwd`, `../../../../server.js`,
`/proc/self/environ`) and confirms responses never contain telltales that
only exist in **this container's actual `/etc/passwd`** (`bin:x:2:2:bin:`,
`sys:x:3:3:sys:`, `www-data` — all deliberately absent from the fake
VFS's much shorter `/etc/passwd`).

**`tests/command-isolation.test.js`** (13 assertions) — confirms
`child_process` is required nowhere in the codebase (the only way Node can
reach real process spawning, so this alone is a complete guarantee — a
supplementary regex for bare `exec()`/`spawn()` calls was tried first and
dropped after it false-positived on `db.exec(query)`, which is `sql.js`'s
safe in-memory SQLite API used by the SQL-injection labs, not
`child_process.exec`). Dynamically sends a `; sleep 4` payload and asserts
the response returns in well under 4 real seconds — the strongest
available proof, since a real shell executing that payload could not
finish in under 2 seconds by definition.

**A design nuance the audit surfaced, correctly handled rather than
"fixed":** `blind-command-injection` *deliberately* delays its response
with a real, capped `setTimeout` to simulate authentic timing-based blind
detection (per its own doc comment in `routes/vulns-injection.js`) — a
slow response there is the intended, pedagogically-correct behavior, not
a violation. My first draft of this test wrongly asserted "must respond
fast" against it and failed; fixed by testing what actually matters for
isolation instead: the ~4s delay for a `sleep 4` payload is genuine (not
a shortcut), and the delay is *capped* — a `sleep 999999` payload still
returns in well under 7 seconds, proving the cap works and an attacker
cannot cause an unbounded hang.

**Two other false positives caught and fixed in this same pass** (see the
test files' own doc comments for the full reasoning): the SSRF test
initially asserted a metadata-service sub-path should be blocked, when the
lab's lookup deliberately matches by host rather than exact path (a
reasonable simulation choice, not a bug); the command-isolation test
initially flagged `db.exec(query)` (sql.js) as a suspected real exec call
before the check was narrowed to precisely `require("child_process")`.

## Phase 5 — Professional Reporting System ✅ DONE (Section 42)

New `src/core/report-engine`, wired into two new endpoints
(`POST`/`GET /api/reports` in `routes/reset-and-validate.js`) and a new
"Write Your Own Report" section added to the training platform's existing
Report tab (`public/js/lab.js`) — the pre-existing Report tab only ever
*displayed* a pre-written reference report; it never let the learner
submit their own.

**Deliberately grounded in real session state, not just a form.** A
report only earns full marks if the submitting session genuinely holds a
real, server-issued flag for the exact lab+difficulty being reported
(checked against `session.flags`, the same source of truth flag-engine
already uses), AND that flag is actually included in the Evidence field.
This mirrors the real bug-bounty workflow the spec asks for: exploit
first, document second — a well-written report with no reproducible proof
still scores 0 on Evidence and gets told exactly why, not silently
accepted.

**Rubric, itemized rather than a single score:** Title, Severity (must be
one of the 5 standard tiers), Affected Asset, Endpoint (must actually
reference `/vuln/<this-lab>`), Description, Steps to Reproduce (counts
distinct steps, not just word count), Impact, Remediation, and Evidence
(worth the same as every other field, but only awarded when verified) —
9 fields × 10 points. Every field gets specific, constructive feedback
either way (e.g. a generic title like "bug" is told exactly why that's a
problem in a real triage queue, not just marked wrong).

**Design decisions worth recording:**
- Reports are stored in `session.reports` and are **not** cleared by
  `resetLabState()` — resetting a lab to practice again shouldn't erase a
  report the learner already wrote and got feedback on. Tested explicitly.
- The existing "Reference Report" content (the pre-written model
  write-up) was kept and relabeled, not removed — the new form sits
  alongside it so a learner can compare their own report against the
  reference after writing it.
- Reports are session-scoped with the same cookie-based isolation as
  every other endpoint — verified a fresh session sees zero of another
  session's reports.

New `tests/report-engine.test.js` (22 assertions) covers: validation,
an unverified report against a never-solved lab, a deliberately weak
report (scores ≤20, flags the generic title and invalid severity), the
full solve → report-without-evidence → report-with-evidence progression,
an endpoint-mismatch case (reporting lab A's endpoint while filing against
lab B), listing/filtering, reset-survival, and session isolation.

## Phase 4 — Attack Chain State Machine ✅ DONE (Sections 32–33)

New `src/core/chain-engine`, wired additively into all 3 existing chains
in `routes/vulns-chains.js` at each real gated transition already present
in that code — no exploit mechanic, response shape, or difficulty
behavior changed. Confirmed by the pre-existing `tests/chains.test.js`
(45 assertions covering the actual exploits) passing completely unchanged
alongside the new tracking.

**ADAPTATION, documented up front in the engine's own header comment:**
the spec's example sequence is `NOT_STARTED -> STARTED -> OBJECTIVE_1 ->
OBJECTIVE_2 -> OBJECTIVE_3 -> EXPLOIT_VERIFIED -> FLAG_ISSUED -> SOLVED`.
This app's 3 chains genuinely have 1, 2, and 3 real gated intermediate
steps respectively — forcing all three into exactly 3 generic
"OBJECTIVE_N" slots would mean inventing fake states for the chains that
don't have 3, or collapsing real distinct steps for the one that does.
Instead each chain declares its own ordered list of meaningfully-named
milestones (e.g. chain-support-takeover's are `CREDENTIAL_LEAK_FOUND ->
AUTHENTICATED -> TICKET_ACCESS_CONFIRMED`) between the fixed, identical
`STARTED` and `EXPLOIT_VERIFIED` bookends every chain shares.

**What actually advances state — verified transition-by-transition, not
just "solve it and check the end state":**

- **chain-support-takeover**: `STARTED` (page load) → `CREDENTIAL_LEAK_FOUND`
  (the correct-tier leaked backup/config file) → `AUTHENTICATED` (real
  successful login) → `TICKET_ACCESS_CONFIRMED` (any ticket viewed while
  logged in) → `EXPLOIT_VERIFIED`/`FLAG_ISSUED` (the actual IDOR target
  ticket reached).
- **chain-internal-pivot**: `STARTED` → `SSRF_KEY_OBTAINED` (SSRF
  genuinely reaches the internal target, not just any URL) →
  `EXPLOIT_VERIFIED`/`FLAG_ISSUED` (the leaked key is used successfully
  against the real admin endpoint).
- **chain-xss-to-admin-action**: `STARTED` → `PAYLOAD_STORED` (a
  genuinely live payload survives the sanitizer — an inert one does not
  advance state) → `ADMIN_EXECUTION_CONFIRMED` (the simulated admin
  review detects it) → `EXPLOIT_VERIFIED`/`FLAG_ISSUED` (the hijacked
  session takes the sensitive action).
- **`SOLVED`** is wired generically for all 3 in one place — a single
  added check in `/api/validate-lab` (`if (C.isChainLab(labId))
  C.advanceChainState(...)`), not duplicated per chain.

New `GET /api/chain-progress/:chainId` exposes the live state, full
history, and `percentComplete` for any of the 3 chains — session-scoped,
same isolation guarantee as every other endpoint. New
`tests/chain-engine.test.js` (34 assertions) covers the engine's pure
state-machine logic directly (never regresses, never skips validation,
unknown states/chains are safe no-ops) plus a real transition-by-
transition walk through all 3 chains, including negative cases (a failed
login, a non-internal SSRF target, an inert XSS payload, a 404'd
wrong-tier leak endpoint) that must each NOT advance state — not just the
happy path.

localhost:3000: PASS
No lab behavior, response shape, or difficulty logic changed in any of

## Phase 7 — A second flaky-test investigation, this one real (not a false alarm)

While wiring up `/robots.txt` (unrelated work), `tests/idor-expert-tier.
test.js` started failing intermittently during full-suite runs. Given the
LAST investigation into "intermittent" failures turned out to be a
misdiagnosed real bug hiding behind confusing grep output, this one got
checked properly and directly rather than assumed to be more of the
same.

**This time it really was in the test, and the root cause was exactly
what had been predicted (but not yet fixed) when the file was first
written**: `ensureUser()` assigns each fresh session a RANDOM real user
id from a pool of 12. The test hardcoded `id: 2` as "the victim" without
checking whether the test's OWN session might randomly be assigned
canonical id 2 itself — about a 1-in-12 chance per run of hardcoding your
own id as your intended target, which of course doesn't get blocked
(you can always see your own profile), and so intermittently, randomly
failed. Fixed by picking a victim id programmatically guaranteed to
differ from the session's actual own id, rather than assuming.

**Fixing it once didn't confirm it was fixed** — ran it 8 times in
immediate succession (not once, not the standalone-passes-so-it's-fine
shortcut) specifically because the whole nature of the bug is that it
only manifests some of the time. Then ran the FULL suite 3 more times
after that. A second, unrelated bug surfaced during THIS same fix
attempt and got caught immediately by the repeated runs: the victim
match regex assumed no whitespace after a JSON key's colon
(`"canonicalId":2`), but `JSON.stringify(obj, null, 2)` pretty-prints
with a space (`"canonicalId": 2`) — an easy one-character regex miss
that would have looked like "still flaky" if not isolated and diagnosed
specifically rather than just re-running until it happened to pass.

**Also checked, proactively, whether the same collision risk existed
anywhere else** — specifically in `tests/graphql-expert-tier.test.js`,
which also hardcodes a victim id (`100`, the admin). Confirmed safe:
`ensureApiUser()`'s random pool explicitly filters `role !== "admin"`
before drawing, so id 100 can never be randomly assigned to a test
session there. Checked the actual source, not assumed.
